# Developing this plugin

The plugin has **no build step for its own code**: `index.js` (Host half) and `client.js` (browser half) run as they are. `vendor/mermaid.esm.min.mjs` is the only generated file, and only needs rebuilding when the bundled Mermaid version changes.

That means a fix is usually: edit a file → restart DSH → look. This page removes the friction around "restart and look".

## Three ways to run it

| Setup | How | Use when |
|---|---|---|
| **Link** (development) | `dsh plugin add` of this checkout, or `plugin_manager` install with the repo path | You are changing the code. Edits apply to the running install; restart DSH to load them. |
| **Published** (normal use) | `dsh plugin --profile <profile> add dsh-mermaid-plus` | You want the released artifact, and fixes arrive by publishing a version. |
| **Copied + patched** | Published install, then `node tools/dev-sync.mjs` | You want to try a fix on a *published* install without releasing. Copies this checkout over the installed package; restart applies it. |

`node tools/dev-sync.mjs --dry-run` lists what it would replace. If the profile already links this checkout, the script says so and does nothing.

## The loop that avoids restarting DSH

Most UI work can be verified **outside** the app:

```sh
node test/serve-e2e.mjs      # serve the harness page on :8732
open http://127.0.0.1:8732/  # 45 assertions run in the page; results in window.__E2E__
```

`test/e2e/simforge.html` is the eyeball page: it reads
`test/e2e/simforge-complex.md` (8 complex diagrams lifted from the SimForge docs),
wraps each fence the way the chat renderer does, and renders them with the shipped
`client.js`. `?dark=1` switches the palette, `?source=1` opens the code views, and
`?md=<file>` swaps the source document. The verdict lands in `<title>`
(`SimForge 8 · ok 8 · fail 0`) and in `window.__SIMFORGE__`.

```sh
node test/render-page.mjs --md=simforge-panorama.md --out=docs/simforge-panorama.png
```

`test/render-page.mjs` drives the same page headless and prints the verdict plus the
first lines of each failed diagram, so a screenshot and a pass/fail check are one
command. `simforge-panorama.md` is the verbatim extraction of all nine diagrams in
《SimForge_当前系统架构与数据流转全景》 (generated by `tools/extract-mermaid.mjs`);
all nine render. The batch sequence diagram used to fail because its `Note` wrote
`GenerateData[A:p1,p2; B:p3]` — an ASCII `;` is a statement separator inside a
`sequenceDiagram`; the source now uses a full-width `；`.

`test/e2e/index.html` loads the **shipped** `client.js`, the real vendored Mermaid, real React, and a DOM that looks like the Chat renderer's Markdown. Add a fixture there for the case you are fixing — a new fence shape, a theme, a viewer interaction — and iterate with a browser refresh instead of an app restart.

```sh
node test/run.mjs            # host route, real cordis mount, jsdom browser-half behaviour
```

## When something breaks in the app

```sh
node tools/doctor.mjs         # activation, install mode, and the last browser events
```

It prints:

- **checkout vs installed versions** and whether the install is a link or a copy;
- the Host half's `activation.json`: package name, route, resolved `clientPath`, and whether this package's browser row was in the client graph;
- the browser half's `report.json`: event counts and the last few events.

Both files live in `<os tmp>/dsh-mermaid-plus/`. They contain **event names and counts only** — no diagram source, no file contents. Browser-side render errors are also printed to the developer-tools console.

### Reading the symptoms

| Symptom | Likely cause | Where to look |
|---|---|---|
| Mermaid blocks show no card at all | The rendered Markdown changed shape, so the block is not recognised | `blocks-unmatched` count > 0 in the report → compare the new DOM with `isMermaidBlock()` |
| Card appears, diagram fails | Mermaid parse error, or the runtime did not load | `render-error` in the report + console; the runtime URL is `<route>/mermaid.esm.min.mjs` |
| Cards disappear after a DSH update | Client bundle not loaded, or the seat moved | `activation.json` (`own entry in client graph`), then the client slots |
| Works in the app, not in a preview (or vice versa) | A renderer with a different DOM shape | Add that shape to `test/e2e/index.html`; `isMermaidBlock()` is the single place that decides |
| Nothing renders after an edit | The app did not reload; the desktop shell does not reliably reload on ⌘R | Restart DSH |
| Console: `slot "<name>" is not declared` | A view injected its parent slot instead of the slot it registers into, so registration ran before the child slot existed. DSH 0.2.2-rc.1 declares parents first | `ctx.slots.inject()` calls in `client.js` |

The decoration layer is the fragile part: it keys on rendered `<pre>` elements because the shipped Markdown renderer exposes no code-fence extension point. If upstream ever adds one, that is the code to replace — the rest (Host route, modes, viewer, settings) survives.

## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request:

```sh
npm ci
node test/run.mjs
node test/run-e2e-headless.mjs   # spawns the page server, drives Chrome, reads <title>E2E n/m
node tools/pack-check.mjs        # asserts the publish whitelist and the vendored runtime
```

`test/run-e2e-headless.mjs` needs a Chrome/Chromium binary. It searches the usual
macOS/Linux names plus the standard Windows Chrome and Edge paths, and
`CHROME_BIN` overrides the search. The page reports its own verdict in the title,
so a browser that renders nothing fails instead of passing vacuously.

One suite is skipped on CI on purpose: `test/host-mount.test.mjs` mounts the
plugin on the real `webServer` service, and CI installs only this package's dev
dependencies. `@deepseek-ai/dsh-host-webserver` from DSH `0.2.2-rc.1` and later
registers `webServer`, which is the generation this plugin targets, so the suite
runs locally once the DSH install is linked into `node_modules`:

```sh
# macOS / Linux — adjust the application path
mkdir -p node_modules/@deepseek-ai
ln -s "/Applications/DSH NEXT.app/Contents/Resources/app/node_modules/@deepseek-ai/cordis" node_modules/@deepseek-ai/cordis
ln -s "/Applications/DSH NEXT.app/Contents/Resources/app/node_modules/@deepseek-ai/dsh-host-webserver" node_modules/@deepseek-ai/dsh-host-webserver
```

```powershell
# Windows — junctions resolve the same way and need no admin rights
$inner = '<dsh-install>\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai'
New-Item -ItemType Directory -Force node_modules\@deepseek-ai | Out-Null
foreach ($p in 'cordis','dsh-host-webserver') {
  New-Item -ItemType Junction -Path "node_modules\@deepseek-ai\$p" -Target (Join-Path $inner $p)
}
```

That runs the mount suite against the **real** 0.2.2-rc.1 services, which is how
a DSH upgrade is cleared: unit suite, mount suite, then the app itself.

## Releasing

完整操作以 [打包发布与更新](打包发布与更新.md) 为准。

本 Fork 通过 GitHub Release 分发 TGZ，不再依赖 npm 发布或 NPM_TOKEN。生成的 TGZ、ZIP 和 dist/ 不进入 Git，已有历史不重写；vendor/ 是运行资源，继续保留。

1. 同步 package.json、package-lock.json 的版本和 README 安装地址。
2. 执行现有检查并打包：

```sh
npm ci
npm test
node test/run-e2e-headless.mjs
node tools/pack-check.mjs
npm pack
```

仅 Mermaid 依赖变化时需先运行 npm run build。

3. 提交源码，推送 main 和与清单一致的版本标签（将 x.y.z 替换为实际版本）：

```sh
git add <本次修改的文件>
git commit -m "调整打包发布与安装说明"
git push origin main
git tag vx.y.z
git push origin vx.y.z
```

release.yml 检查标签版本、运行原有测试和包清单检查，在 dist/ 生成 TGZ 与 SHA256SUMS.txt，上传至草稿 Release，成功后公开。仅需 GitHub 自带的 GITHUB_TOKEN。手动运行只验证并保存 Actions artifact，不发布。

4. 从 README 的固定版本 Release 地址下载 TGZ 和 SHA256SUMS.txt，核对哈希、包内版本与必要运行文件。确认附件可下载后，安装命令才可用。安装和更新见 [README](../README.md#install)。发布不会自动更新本机。

package.json 的 files 是安装包白名单；工具、测试和 Docs 不进入 TGZ。

## Compatibility

Verified against DSH `0.2.2-rc.1`. DSH is a developer preview; client plugin contracts, slot keys and rendered Markdown can change between releases. Treat a DSH upgrade as a test run: `node tools/doctor.mjs`, then open a conversation with a diagram and a preview.
