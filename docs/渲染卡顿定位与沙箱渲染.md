# 渲染卡顿的定位与 iframe 沙箱方案

> 记录一次真实排查：同一份 Mermaid 源码，在干净测试页里约 200 ms，在 DSH 对话页里要 3.4–8.5 秒。结论是「量文本的文档环境」而不是「ELK 布局算法」慢，最终把渲染搬进最小同源 iframe 解决。
> 适用版本：0.4.4 → 0.5.0（2026-11-15）。

## 1. 现象

- 打开含图对话、或滚动到图表附近，页面整段卡住数秒；`卡死` 时长与图的大小正相关。
- 同一张图在 `test/e2e/simforge.html`（干净页面、同样 Mermaid 12.2.0、同样 `layout:'elk'`、同样 redux 配色）约 200 ms 出图。
- 关闭 dsh-marktext 插件后确认渲染来自本插件，问题可复现。

## 2. 定位手段

### 2.1 把耗时拆成可归因的数字

`client.js` 的 `report-ok` 事件写入 `%TEMP%\dsh-mermaid-plus\report.json`，0.4.6 起带：

| 字段 | 含义 |
|---|---|
| `renderMs` | `mermaid.render()` 内部耗时（解析 + ELK + 测量 + 生成 SVG） |
| `mountMs` | SVG 插入卡片、`paint`、`applyZoom` 的耗时 |
| `nodes` | 当时页面节点数 |
| `jank` / `jankMax` | 挂载以来 ≥100 ms 长任务的次数与峰值 |
| `via` | `sandbox` 或 `inline`（0.5.0 起） |

实测（web profile，DSH 对话页）：

```
renderMs 8203  mountMs 55  nodes 6237
renderMs 6903  mountMs 56  nodes 6526
renderMs 3516  mountMs 56  nodes 6757
renderMs 2043  mountMs 54  nodes 6923
```

`mountMs` 只有 35–56 ms，`renderMs` 是 1.5–8.2 秒。**插入不慢，渲染慢**，且慢在同一条 `mermaid.render()` 调用里。

### 2.2 排除宿主页面的其他嫌疑

- 不是 ELK 算法本身：同一张图在干净页里 150–200 ms。
- 不是 CSS 规则数量单独造成：往测试页注入 6000 条规则 + 4000 个节点，9 张图总阻塞仅 1.3 s → 2.0 s（约 1.5 倍），远不到 20–40 倍。
- 不是节点数线性放大：真实会话 `nodes` 5–7 千，与注入测试同量级。

因此差异只能来自 **Mermaid 在哪个文档里做文本测量与 SVG 布局**：`getBBox`/`getComputedTextLength` 依赖文档的样式与布局上下文，宿主应用的样式表与深层 DOM 让每次测量都变贵，而一张流程图要做几百次测量。

## 3. 为什么不能真的「拆进程」

| 方案 | 为什么不行 |
|---|---|
| Web Worker | Worker 无 DOM，`getBBox` 不存在；jsdom 量出来是 0，布局会错 |
| 同源 iframe | 与主页面共享同一渲染主线程，只是把测量环境隔离，不能解 CPU 占用（但正是这一点解决了本例） |
| 跨源 iframe（OOPIF） | 也许能拿到独立进程，但依赖站点隔离策略、CSP 与端口，不可控 |
| 服务端渲染 | 需要 headless Chrome（mermaid-cli 路线），单张图 1–2 秒且要维护浏览器进程，比现状更差 |
| 自研 worker 版 ELK | Mermaid 12 的 `registerLayoutLoaders` 契约是「loader 返回的 `render()` 直接产出 SVG」，要换就得重写该渲染器，属于 fork |

## 4. 解决方案：最小同源 iframe 沙箱

### 4.1 结构

- Host 半（`index.js`）新增两条静态资源：`renderer/renderer.html`、`renderer/renderer-frame.js`，由插件路由 `/x-dsh-mermaid-plus/` 提供。
- `renderer.html` 只有 reset、字体和 Mermaid 入口，没有任何应用样式。
- `renderer-frame.js` 监听 `postMessage`，串行执行 `mermaid.render`，回传 `{ id, svg, ms }`；校验 `event.source === window.parent` 与同源 origin。
- 浏览器半（`client.js`）创建一个离屏 `iframe`（1×1、`aria-hidden`、`pointer-events:none`），请求/响应经 `postMessage` 往返；主页面只负责插入 SVG 与卡片交互。

### 4.2 降级与预热

- 沙箱是优化不是依赖：`ready` 超时、渲染超时、iframe 被 CSP 拦截，都会置 `sandboxFailed` 并回退到页内渲染（`via:"inline"`）。
- 页面空闲预热改为「预热沙箱」：load 之后在 `requestIdleCallback` 里建 frame，让 5.2 MB 运行时在用户滚动前就绪；`manual` 模式与 `save-data` 连接跳过。
- jsdom 测试环境没有 `requestIdleCallback`，因此测试走页内路径，沙箱代码在真实浏览器里由 e2e 页面覆盖。

### 4.3 效果

`test/e2e/simforge.html?md=simforge-panorama.md`（9 张图，真实浏览器）：

| 指标 | 改造前 | 沙箱后 |
|---|---|---|
| 长任务数（≥100 ms） | 14 | 5 |
| 总阻塞 | ~1.4 s | ~0.7 s |
| 最长任务 | 190–314 ms | 376 ms（含 5.2 MB 首次解析） |
| 渲染结果 | 9/9 | 9/9 |

DSH 对话页的整段卡顿消失（用户体感确认）；`renderMs` 的具体数值以新会话日志里的 `via:"sandbox"` 记录为准。

## 5. 同期做的其他缓解

按影响排序，这些是沙箱之外的「少干一点活」：

1. **滚动避让**：scroll 停止 140 ms 后才开始渲染，避免与滚动抢主线程。
2. **队列让出**：多张图排队时，每条之间 `requestIdleCallback` 让出（单张仍立即开始）。
3. **缩放重排合并**：`ResizeObserver` 通知合并到一个 `rAF`，N 张卡一次布局；不再每张卡各自读 `clientWidth`。
4. **预热延后**：运行时预热放到 `load` 之后，避免边加载对话边编译 5 MB。
5. **静态资源 gzip + ETag + immutable**：5.2 MB → 1.57 MB，重复访问 304。

## 6. 复现与验证命令

```sh
node test/render-page.mjs --md=simforge-panorama.md   # 9/9 或按 via 判断走的哪条路径
node test/serve-e2e.mjs                               # 浏览器里看 http://127.0.0.1:8732/simforge.html
```

诊断数据：

```powershell
$f = Join-Path $env:TEMP 'dsh-mermaid-plus\report.json'
Get-Content $f -Raw | ConvertFrom-Json | Select-Object -Last 10 |
  ForEach-Object { "$($_.receivedAt) $($_.event) $($_.href) $($_.detail | ConvertTo-Json -Compress)" }
```

判断口径：

- `via:"sandbox"` 且 `renderMs` 数百毫秒 → 正常；
- `via:"inline"` → iframe 被拦或沙箱超时，看 Host 是否提供 `renderer.html`、页面 CSP 是否允许 `frame-src`；
- `mountMs` 变大（>500 ms）→ 宿主页面重排问题，与 Mermaid 无关，另查。

## 7. 遗留

- 沙箱与主页面共享主线程：单张超大图（数千节点）仍会阻塞，只是回到「干净页」的量级。
- 沙箱内没有宿主页面的字体与继承样式，文字宽度理论上可能与页内渲染略有差异（未逐项核对像素）。
- 若后续要支持「无 iframe 环境」（如某些嵌入式 WebView），页内路径保留，但需重新评估卡顿。
